# Процедура аудита ML-экспериментов

4. **`02_lab_chat_DRAFT.md`** — архив обсуждений (не меняет политику, игно

**Важно:** Никогда не делайте выводов на основе архивных обсуждений или собственных предположений. Работайте только с фактами из протоколов.

---

## Алгоритм аудита

### Шаг 1: Загрузка контекста

1. Извлеките из `01_audit_policy.md` все категории нарушений и их определения
2. Из `03_domain_scope.md` зафиксируйте специальные проверки:
   - Для временных рядов: проверяйте доступность признаков на дату прогноза
   - Для групповых данных: проверяйте единую единицу независимости (пациент, проект, устройство)
3. Определите общую цель аудита: отделить подтверждённые ошибки от корректных решений и случаев нехватки информации

### Шаг 2: Анализ каждого эксперимента

Для каждого эксперимента из `cases/evaluation.json` выполните:

#### 2A. Определите контекст эксперимента

Извлеките из полей `goal` и `protocol`:

| Параметр | Что искать | Пример |
|----------|-----------|--------|
| **Цель обобщения** | На какие новые данные должна работать модель? | "новые пациенты", "будущие периоды", "новые проекты" |
| **Единица независимости** | Что является независимым примером? | пациент, проект, устройство, изображение |
| **Дата прогноза** | Для временных рядов: на какую дату делается прогноз? | "январь 2026", "следующий месяц" |
| **Сценарий внедрения** | Как модель будет использоваться в продакшене? | IID-выборка, временной ряд, групповой split |

#### 2B. Проверьте каждую категорию нарушений

Проверьте протокол по каждой категории из политики. Используйте таблицу:

| Код | Что искать в протоколе | Ключевые слова-индикаторы |
|-----|------------------------|---------------------------|
| **TARGET_LEAKAGE** | Признаки, доступные только после момента прогноза | "заполняют через 90 дней", "после закрытия", "фактическое значение" |
| **TEMPORAL_LEAKAGE** | Данные из будущего относительно даты прогноза | "использованы данные сентября для прогноза января", "будущие значения" |
| **GROUP_LEAKAGE** | Пересечение групп между train и test при заявленной оценке на новые группы | "визиты одного пациента в обеих выборках", "проекты повторяются" |
| **PREPROCESSING_LEAKAGE** | Параметры преобразований рассчитаны до разбиения на train/test | "рассчитали по всему датасету", "до разбиения", "target encoding заранее" |
| **TEST_TUNING** | Многократное использование test для выбора модели/порога/гиперпараметров | "14 раз запускали", "выбрали по лучшему test", "подбирали на test" |
| **SHIFT_UNVALIDATED** | Смена распределения без проверки на новых данных | "датчики заменили", "сменили процесс", "не проверяли на новых данных" |
| **METRIC_MISMATCH** | Заявленная метрика скрывает невыполнение прикладной цели | высокая accuracy при сильном дисбалансе классов |
| **DUPLICATE_LEAKAGE** | Дубликаты/аугментации по разные стороны разбиения | "аугментации", "дубликаты", "копии" |
| **IRREPRODUCIBLE** | Заявлена воспроизводимость, но процесс не позволяет повторить | нет seed, нет версии данных, нет фиксированных гиперпараметров |

**Важно:** Не отмечайте все возможные риски "на всякий случай". Требуется привязка к конкретному факту из протокола.

#### 2C. Классифицируйте эксперимент

На основе проверки определите вердикт:

**FAIL** — подтверждено ≥1 нарушение:
- Заполните `flags` кодами всех подтверждённых нарушений
- В `evidence` укажите конкретный факт из протокола (цитата или точное описание)
- В `next_step` предложите конкретное исправление для этого эксперимента

**PASS** — нарушений нет:
- `flags` — пустой массив
- В `evidence` объясните, почему протокол корректен (какие принципы соблюдены)
- В `next_step` укажите, что зафиксировать для воспроизводимости (seed, версия данных, гиперпараметры)

**NEED_INFO** — не хватает данных:
- `flags` — пустой массив
- В `evidence` укажите, каких фактов не хватает для вынесения вердикта
- В `next_step` сформулируйте конкретные уточняющие вопросы

**Критические правила:**
- Отсутствие описания ≠ доказанное нарушение → используйте `NEED_INFO`
- Если подтверждено нарушение в одной части протокола, не заменяйте `FAIL` на `NEED_INFO` из-за неохваченных частей
- Высокая метрика сама по себе не означает ошибку

### Шаг 3: Формирование вывода

Сформируйте JSON-массив по одному объекту на каждый эксперимент:

```json
{
  "id": "EXP-XX-YY",
  "verdict": "FAIL|PASS|NEED_INFO",
  "flags": ["CODE1", "CODE2"],
  "evidence": "Конкретный факт из протокола с привязкой к тексту",
  "next_step": "Конкретное действие для исправления или воспроизводимости"
}
